# 第一个模块：首版范围讨论稿

日期：2026-09-14；状态：draft，待审阅。

本文将已有调研转换为可讨论的首版范围建议。用户已表达以 Sub2API 作为第一个模块脚手架的方向；下列具体范围、运行模式及实现方案尚未逐项确认。本文不代替正式 Spec，也不代表已完成运行验证。

## 1. 首版希望达到什么效果

建议首版目标：管理员能够把公司已经运行的私有模型开放给指定研发人员，集中发放访问 Key，限制可访问的模型与同时请求数，查看使用情况，并能停止某个人继续使用。

先选择一个私有模型服务和一种实际使用的开发工具作为后续验证对象，跑通完整流程；具体模型、工具和版本待讨论。基础能力继续复用 Sub2API 的多用户、分组和上游账号结构，不将实现写死为一个模型。

“模型服务”指已经提供调用地址的模型程序；“Key”是研发工具访问管理平台的凭证；Sub2API 的“上游账号”保存平台访问模型服务所需的地址和凭证。这两类凭证的用途不同。

## 2. 建议跑通的操作流程

| 步骤 | 谁操作、做什么 | 希望得到的结果 | 实现依据 |
| --- | --- | --- | --- |
| 1 | 管理员登记私有模型的地址、凭证和模型名 | 平台能将请求转发给该服务 | 已有配置和聊天转发路径，实际兼容待验证 |
| 2 | 管理员配置访问分组、模型白名单和上游账号并发 | 明确哪些模型可用，以及该账号同时转发多少请求 | 已有实现；账号上限不自动等于整个模型服务总上限 |
| 3 | 管理员创建研发人员用户、授予分组权限并设置用户并发 | 每个人都有独立归属和访问范围 | 已有页面；需正确配置公开/专属分组权限 |
| 4 | 管理员为指定用户创建 Key，并交付入口地址、Key 和模型名 | 研发人员获得属于自己的访问凭证 | 集中代发需补入口；具体交付方式待讨论 |
| 5 | 研发人员在选定开发工具中配置并调用 | 正常请求获得回答，流式回答能逐步显示 | 接口有源码依据；工具所需协议和功能待核对 |
| 6 | 管理员查看用户、Key 和模型的使用记录 | 能知道谁在使用、用了多少、耗时如何 | 复用已有用量页面；数据完整性待后续验证 |
| 7 | 管理员停用普通用户 | 阻止该用户后续访问 | 已有状态修改和认证检查；不承诺立即终止在途请求 |

## 3. 建议直接复用的范围

优先沿用现有页面、数据结构与服务逻辑，减少需要长期维护的自有代码。

| 能力 | 首版建议 | 需要注意的条件 |
| --- | --- | --- |
| 管理员后台及用户管理 | 复用用户创建、编辑、状态管理 | 不新增公司组织层级或复杂角色体系 |
| 模型服务接入配置 | 复用 OpenAI 兼容 APIKey 账号路径 | 协议、内网地址策略、模型名称映射要与实际服务匹配；“OpenAI 兼容”不表示必须使用 OpenAI 云服务 |
| 用户访问权限 | 复用分组授权与模型白名单 | 分组暂作为访问配置；不直接等同部门。公开分组默认可绑定 |
| 并发限制 | 先复用用户级、上游账号级上限 | 具体数值后续结合容量确定，不能仅凭 8 张 H200 推算；Key 级并发限制未确认有实现 |
| 用量与耗时查询 | 复用现有统计和筛选页面 | 先观察 Token、请求记录和耗时；费用统计是否承担内部配额职责待讨论 |
| 停用用户 | 复用现成操作 | 影响该用户整体访问；单 Key 停用另行讨论 |

## 4. 建议补充与待决定的范围

### 建议补充：管理员集中代发 Key

这是当前最明确、与用户已表达方向一致的功能缺口。建议在现有用户 Key 管理位置增加“为该用户创建 Key”的操作，复用底层生成、归属和持久化能力。创建后的 Key 必须属于目标用户，调用记录也应归到该用户。

基本代发初步涉及管理页面和后端管理员入口；现有用户归属字段有复用基础，暂未发现基本功能必须新建数据表的理由。具体接口、字段和权限检查留到设计阶段确定，不直接绕过普通用户接口的归属校验。

### 待讨论：决定首版行为的几项选择

| 事项 | 建议讨论起点 | 为什么需要决定 |
| --- | --- | --- |
| 研发人员是否需要登录平台 | 先让日常模型调用仅依赖 Key；是否开放自助后台另定 | 管理员代发不自动意味着必须禁止自助创建；关闭入口也不能只隐藏按钮 |
| 管理员可对 Key 做哪些操作 | 代创建优先；单 Key 停用/重新发放是否同批纳入待定 | 停用整个用户已有，但丢失一把 Key 时可能只需替换该 Key；重新发放不能让旧 Key 无意保留有效 |
| Key 如何交付 | 首版可考虑管理员在创建后手工交付，暂不开发自动通知 | 需要明确创建后展示、后续能否查看以及接收方式；本稿不指定外部发送渠道 |
| 是否要求 Key 到期失效 | 明确是否是首版必须，再选运行模式 | Simple Mode 的所读路径跳过到期检查，不能直接沿用界面字段便宣称到期会生效 |
| 是否需要个人用量硬配额 | 建议先区分“看用量”和“达到阈值拒绝调用” | 现有 Key 额度按金额计量，不能直接当作 Token 数或请求次数配额；若首版必须，需继续核对定价及扣减。见[配额机制核对](quota-mechanism-review.md)：金额代理路线已放弃 |
| 是否限制请求频率和上下文 | 分别判断首版是否必须 | RPM 是每分钟请求数；上下文是单次输入与输出长度。两者不由并发限制替代，严格上下文检查仍未闭合 |
| 优先支持哪种开发工具 | 选公司最先实际使用的一种，并记录版本和所需能力 | 普通聊天、流式回答和工具调用不是同一个兼容性结论；工具调用指模型要求客户端执行函数或命令，编程 Agent 可能依赖它 |

上表均为待讨论，不因本文给出建议就视为用户已同意。标准模式与 Simple Mode 暂不选择；其差异需要与到期、配额和计量需求一起确定。

## 5. 建议暂缓的自研工作

下列是首版建议，不代表删除长期需求，也不要求从上游产品移除已有功能。

- 新建一套管理界面、统一改造所有页面或大规模重构后端。
- 批量开户、审批流、部门层级、复杂角色和自动发 Key 通知。
- 自建充值、支付、套餐运营流程。
- 一次性兼容所有开发工具和模型协议。
- 在第一个模块内实现模型安装、启动/停止、GPU 分配和 Kubernetes 集群管理。这些继续属于其他大模块。
- 自建完整监控平台或承诺保存全部对话。首版优先复用请求用量与耗时查询，跨模块运维另行规划。

## 6. 后续验证应证明什么

以下是未来验收讨论的起点，尚未执行。当前继续遵循只做文档和源码核对、暂缓部署实验的安排。

1. 指定用户拿到属于自己的 Key，能在选定工具中调用指定私有模型；按实际工具验证普通回答、流式输出和必要的工具调用。
2. 未授权分组或模型的请求被拒绝；管理员代发不能给目标用户无意扩大权限。
3. 用户及账号并发达到设定值时，行为符合最终约定；请求结束后名额释放。
4. 调用记录能关联正确的用户、Key 和模型，Token 数据来源与缺失行为有说明。
5. 停用用户后，新请求被拒绝；缓存传播与在途请求的行为有实际证据。
6. 若最终纳入单 Key 停用、有效期或硬配额，则分别验证其生效，不能由停用用户或界面字段推定通过。

## 7. 范围讨论之后的工作顺序

1. 先讨论第 4 节的选择，形成明确的首版操作范围。
2. 对影响选用 Sub2API 的未闭合项做有针对性的源码核对，重点是目标工具协议、运行模式与计量。
3. 整理源码纳入仓库的方案：固定版本、代码位置、上游来源与许可证保留、以后同步更新的方式和自有改动记录。方案确定后再纳入源码，本稿不决定 fork、subtree 或其他方式。
4. 将确认后的模块方向与范围提炼进正式项目文档，再按独立开发范围拆 Spec，编写 proposal、design、api_schema 和 task。

Git 提交仍由用户审阅提交范围、说明和验证情况后明确同意。本文完成不表示进入编码或提交阶段。
