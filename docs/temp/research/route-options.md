# 第一模块技术路线比较

Sub2API 后续证据见 [源码核对](sub2api-source-review.md)：私有聊天路径与用户/账号并发有实现，可继续评估现成后台路线；简化模式跳过所读认证中的 Key 到期/额度检查，需要计入适配成本。

候选更新：新增 [Sub2API](notes/sub2api.md)，作为现成平台第三候选。下面两条路线是此前深入核对结果，暂不为只有初筛证据的 Sub2API 估计改造量；先核对私有模型接入及内部团队模式。

日期：2026-09-14。状态：待讨论，未选型。依据：[源码复核](source-review.md)及[最小改造清单](minimal-adaptation.md)。仅静态调研。

## 已明确的取舍

开发人力为一人借助 Agent，优先复用成熟产品及后台，先跑通接入、发 Key、调用、限制和统计流程，再扩展。当前主候选收敛为 New API、LiteLLM；One API 保留历史参考。此前默认 LiteLLM 需要配合自研后台的路线已调整。

| 路线 | 优先复用 | 决策关键点 |
| --- | --- | --- |
| New API 现成后台与服务，按缺口扩展 | 用户、Key、渠道、请求频率限制及日志 | 并发/上下文尚待确认；分组不等于公司团队体系；AGPLv3 条件需符合公司计划 |
| LiteLLM 现成后台与网关，按缺口扩展 | Key、用户/团队相关管理、模型配置、路由、并发和统计 | 页面操作和商业开关需核对；并发有配置及降级条件；上下文依赖计数与模型信息 |

不预设需要两套网关叠加，也不预设需要开发新的前端。只有明确缺口才进入扩展设计。

## 对技术栈的影响

- New API 采用后将受上游 Go 服务及前端、数据库结构影响，修改越多，跟随上游升级的合并工作越多。
- LiteLLM 采用后需要维护其服务及数据库/缓存依赖；后续通过 HTTP 管理接口扩展其他模块，不必与网关使用相同语言。
- 两者均不自动提供公司所需的完整模型部署与 GPU 调度系统。
- 上述是候选技术约束，不是 x-api-master 已确认技术栈。

## 推荐方式

以最小改造清单核对配置入口、必要代码修改、授权边界和待确认事项。当前不足以判定总体改造成本最低者；LiteLLM 并发证据较直接，New API 完整业务产品形态值得继续比较。不用充值、分销等未提出的功能为候选加分。

下一步先补齐后台操作链、并发启用路径、上下文策略和必要功能授权边界。暂不部署，不建立 Spec，不估算缺乏依据的开发人天。
