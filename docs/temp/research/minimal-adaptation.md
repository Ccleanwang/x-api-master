# New API / LiteLLM 最小改造清单

新增第三候选的同类核对见 [Sub2API 源码核对](sub2api-source-review.md)末尾最小改造表；本文保留原两项目比较，不表示当前候选仍只有两个。

日期：2026-09-14。状态：待讨论，未选型。

后续核对见 [后台操作与限制机制](operation-path-review.md)：New API 已闭合自助 Key 管理路径，集中代发尚未确认；LiteLLM v3 hook 默认映射及注册已定位；上下文计数失败可能继续转发。以下清单结合该文阅读，不把配置复用候选视为已运行通过。

## 目标与前提

- 开发人力为一人借助 Agent，优先复用成熟产品及现有后台，先跑通流程，再扩展。
- 当前主要候选仅 New API 和 LiteLLM。One API 保留历史参考；不因继承关系就将 New API 视为 One API 官方新版。
- 以已运行的私有模型服务为接入对象，讨论“接入 → 发 Key → 调用 → 限制 → 查看统计”。这只是第一模块的比较场景，模型部署和 GPU 调度仍在项目总体范围内。
- 本文整理已有证据，未新增源码验证、部署实验或功能测试；不确定项不直接判成开发任务。不建立 Spec，不锁定技术栈。
- 证据采用 [源码复核](source-review.md) 的固定版本：New API `04c64734cc7c2e58a9efd0b247182330f3f52cce`；LiteLLM `30f33a949b8a2bb890a2baee18e2ab7ab015a4f7`。N1–N3、L1–L3 对应该文中的源码链接。

## 分类口径

- **配置复用候选**：已有相关实现，优先使用现有设置/API/页面；尚不等于已证明全流程无需代码。
- **待确认**：证据不足或操作路径未闭合，不能预先估计改造量。
- **条件扩展**：仅当现有能力不能满足最终要求时，才补充实现。
- **授权边界**：功能是否能用于公司的拟定场景，需单独核对许可证或商业开关。

## 可能需要扩展的边界

| 条件 | 扩展方向 | 目前是否确定要开发 |
| --- | --- | --- |
| 现有并发机制不能满足按用户/模型或集群总量的要求 | 补充请求名额申请、释放、超时和异常恢复 | 否；New API 能力未查清，LiteLLM 有条件实现 |
| 无法准确执行私有模型上下文策略 | 补充模型计数配置或校验逻辑 | 否；先确定策略和上游能力 |
| 公司需要完整部门层级、团队负责人和委派管理 | 映射组织关系或集成公司身份系统 | 否；现阶段未明确需要完整组织系统 |
| 现有统计页面缺少关键视图 | 最小页面调整或新增查询 | 否；需先核对现有页面 |
| 后续需要统一部署模型和分配 GPU | 对接其他模块的管理入口/API | 属于后续总体规划，不计入当前 API 闭环的必要改造 |

## 授权与复用条件

- New API：AGPLv3，修改版网络服务向交互用户提供相应源码的要求需与公司的使用/修改计划一致。不能预设内网免除，也不能笼统解释为公司全部代码必须公开。证据 N3。
- LiteLLM：根目录 MIT 范围与 enterprise 单独授权应分开核对。已读认证中 JWT Auth 有商业开关；普通 Key、Team 表或后台页面存在，不等于所有企业功能免费。证据 L1/L3。
- 暂未要求企业单点登录或完整企业审计，不能因此立即判定必须付费，也不能承诺所有后续需求都免费。

## 当前判断

两者都应先按“现成后台 + 配置”评估，暂不启动自研管理层。New API 是偏完整分发产品的候选，LiteLLM 也包含管理能力且并发控制证据更直接。目前未证明任何一方能零改造覆盖全部闭环，不给出缺乏依据的人天估算或最终排名。

下一轮静态核对仅优先关闭四项：

1. 四类后台页面到管理 API 的操作链，尤其 Key 创建/禁用和统计查询。
2. New API 是否已有推理并发控制；LiteLLM 并发实现如何启用。
3. 两者私有模型上下文检查的配置、计数与失败行为。
4. 上述必要功能的授权开关与许可证条件。

完成这些核对后再给出“最少自主开发工作”的推荐。历史能力矩阵是线索索引，本文未确认的项目不得因旧矩阵出现勾号而当作已验证。
