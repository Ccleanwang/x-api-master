# 第一个模块：MVP 边界决策记录

日期：2026-09-15；状态：draft，待用户审阅。本文记录[首版范围讨论稿](module-1-first-release-scope.md)第 4 节七项选择的逐项结论，其中第 5 点（用量硬配额）在[配额机制核对](quota-mechanism-review.md)后重开并改判。本文不代替正式 Spec，也不代表已进入编码阶段。

## 1. 七项选择的结论

| # | 事项 | 结论 | 依据或代价 |
| --- | --- | --- | --- |
| 1 | 研发人员登录 | 不登录，仅用 Key 调用 | 用户记录仍必须建立，作为 Key 归属与用量统计的容器；停用经管理员改用户状态生效 |
| 2 | 管理员 Key 操作 | 代创建 + 单 Key 停用 | 不做原子轮换。代创建与停用在实现成本上不同量级，见第 3 节 |
| 3 | Key 交付 | 手工交付 + 内置说明模板 | 依赖"创建后可见明文 Key"，该前置未闭合 |
| 4 | Key 自动到期 | 不做 | 收回靠停用。该选择曾用于回避标准模式，第 5 点改判后不再构成约束 |
| 5 | 用量硬配额 | 做。每人一个每日 Token 额度 | 放弃金额代理；改用 `user_platform_quotas` 承载，见第 2 节 |
| 6 | 请求频率 / 上下文 | 做 RPM 且必须核实生效；上下文不设网关层限制 | 上下文依赖上游模型自身拦截，属上游责任 |
| 7 | 优先工具 | 编程 Agent | 工具调用兼容性因此成为必核项 |

七项均尚未经用户逐条确认的仅剩本表汇总本身。

## 2. 第 5 点的重开与改判

原讨论稿第 4 节对"个人用量硬配额"的建议是先用金额代理跑通。[配额机制核对](quota-mechanism-review.md)表明该前提不成立：计价包含模型特定强制价格、高峰倍率、Fast 档倍率与长上下文阶梯，USD 与 Token 数之间不存在稳定换算关系。该路线已放弃。

改判后的方案：以 `user_platform_quotas` 表承载每人每日 Token 额度。该表的按人唯一约束、自然日窗口、管理员接口与审计链均已具备，差距仅在累加与判断所用的量由 `ActualCost` 改为 Token 数。

## 3. 运行模式与配置形态

**结论：采用标准模式。**

此前担心"标准模式会把私有模型请求误拒"经核实不成立。`checkBalanceEligibility` 的判定是 `balance <= 0` 即拒，而用户余额初始值可配置：`GetDefaultBalance` 读取系统设置 `default_balance`，回退到配置默认值；创建用户时亦可通过 `initial_balance` 逐个指定。

配置形态为三个常量：

| 配置项 | 值 | 作用 |
| --- | --- | --- |
| `run_mode` | `standard` | 保证配额检查生效；Simple 模式下 `CheckBillingEligibility` 直接返回 |
| `default_user_balance` | `999999999` | 占位值，越过 `balance <= 0` 的资格闸 |
| 私有模型定价 | `0` | `ActualCost` 恒为 0，余额永不消耗 |

余额取明显偏离真实量级的占位值，是为了让页面上的余额数字不被误读为真实余额。定价为 0 在代码中有明确语义（显式 0 表示该项免费）。

## 4. 额度体系的选择

**结论：只启用体系 B，Key 上现成的 5h/1d/7d 金额窗口不使用。**

`evaluateRateLimits` 的三处判断均带 `RateLimitXx > 0` 前置条件，字段留空（0）时自然全部通过。因此停用体系 A 无需代码改动，只需在配置与操作文档中明确"这些字段不填"。

该选择的代价是首版不具备细粒度突发控制，突发由用户并发上限与 RPM 承担。收益是管理员只需查看一处即可解释"为什么被拦"。

## 5. Token 计算口径

**结论：计入 input + output + cache_creation + cache_read 四类，同等权重。**

不采用按输出加权或排除缓存 token 的方案。理由：口径最简单、最易解释，且缓存命中同样消耗预填充算力，计入才能真正拦住资源占用。代价是多轮对话反复读缓存时额度消耗较快，该现象需在操作说明中提示。

## 6. 必须写入设计的时序特性

额度检查与用量累加不在同一时刻：

- `checkUserPlatformQuotaEligibility` 在**请求进入时**比较用量；
- `IncrementUserPlatformQuotaUsage` 在**响应结束后**异步累加。

因此同一时刻在途的请求会同时通过检查，**额度允许被超出**，超出幅度由并发上限决定。例如剩余额度 1000 token、用户并发为 4 时，四个各带 5000 token 的请求可能全部放行。

该能力的准确定位是**防滥用的配额**，不是**精确计费**。此定位需在设计与验收标准中明确，避免后续把超额误判为缺陷。

另据前轮证据，流式响应中断且已产生部分用量时，已产生的部分会被保留并记账；只有完全无法取得 usage 时才不计数。

## 8. 尚待处理

1. **Key 明文可见性**：已于 2026-09-15 闭合，见 [首版阻塞项核对](sub2api-mvp-blockers-review.md)。DTO 层完整映射 `Key` 字段，交付方案成立；管理端确无代创建处理器，需新开发。
2. **工具调用兼容性**：已于同日核对。网关侧透传路径可用，但**必须显式配置 `openai_responses_mode=force_chat_completions`**，否则 `auto` 会默认走入协议转换路径。上游模型的函数调用能力仍需运行验证。
3. **上游 usage 返回**：决定额度是否真正拦得住人，只能运行验证。
4. **操作流程与配置说明**：七项结论需整理为管理员的实际操作步骤，含"哪些字段留空""余额为占位值""账号模式须设 force_chat_completions"等易误操作点。
5. **源码纳入仓库方案**：固定版本、代码位置、许可证保留与后续同步方式，确定后再纳入源码。
6. **列表接口明文暴露的取舍**：Key 列表响应同样包含完整明文 Key，需决定是否在响应层截断。
