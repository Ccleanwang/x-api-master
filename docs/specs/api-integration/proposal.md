# 统一 API 接入与业务管理 项目提案

对应模块一（[项目说明](../../project.md) 第 3.1 节），Spec ID `SPEC-001`。

## 1. 背景与动机

### 1.1 背景

公司已规划在内网自有硬件上部署 DeepSeek V4.1 Flash 模型服务（vLLM）。模型服务就绪后，研发团队需要一个统一的访问入口，而不是各自直连推理服务。

本模块的前期调研已完成，结论见 [`docs/research/api-integration.md`](../../research/api-integration.md)，支撑证据保留在 `docs/temp/research/`。调研确定了以 Sub2API 作为脚手架，并明确了首版边界。

**自建推理服务是既定前提。** 出于数据安全考虑，模型须部署在内网自有硬件，不存在采购官方云服务的选项。因此上游是自建服务，官方服务不在可比范围内。

### 1.2 问题

模型服务本身只提供推理接口，不解决以下问题：

| 问题 | 后果 |
| --- | --- |
| 谁可以访问 | 无准入控制，推理服务直接暴露 |
| 用了多少 | 无按人聚合的用量记录 |
| 用超了怎么办 | 无额度约束，个别人的大量调用会占用共享算力 |
| 怎么收回 | 无停用手段 |

其中**算力滥用**是核心动机：GPU 算力是全团队共享的稀缺资源，缺少按人配额时，个别人的高强度调用会直接影响他人。

### 1.3 动机

本模块是全项目的**数据源头**：它的库表结构、服务边界与部署形态会成为模块二、三、四的既成约束。先建立它，后续模块的调研与设计才能落在真实约束上。

## 2. 项目目标

### 2.1 主要目标

- 为研发人员提供统一的模型访问入口，按 Key 调用，无需登录平台。
- 由管理员集中发放访问凭证，并能按人收回。
- 按人设置每日 Token 额度，防止算力滥用。
- 按人、Key、模型、时间查看用量。
- 支持编程 Agent 的工具调用场景。

### 2.2 目标产出

- 基于 Sub2API 的可运行服务，含私有模型接入、用户与分组、Key 管理与额度约束。
- 管理端代发 Key 与单 Key 停用能力（Sub2API 现无，需开发）。
- 额度计量由金额改为 Token 的改造。
- 部署与配置说明，含首版所需的配置清单。
- 验证材料：静态核对记录、层级 1 本地验证结果、层级 2 运行时验证结果。

### 2.3 成功标准

- 管理员能创建用户、配置分组与模型白名单、代发 Key 并交付给指定人员。
- 研发人员用该 Key 能通过平台访问私有模型，并能在编程 Agent 中完成多轮工具调用。
- 当日用量达到设定额度后，该用户的后续请求被拒绝。
- 能按人查看当日 Token 用量。
- 管理员停用某用户后，其全部 Key 立即失效。

## 3. 项目范围

### 3.1 包含范围

| # | 范围项 |
| --- | --- |
| 1 | 私有模型接入：OpenAI 兼容上游账号、自定义地址、模型映射 |
| 2 | 用户与分组：用户记录、分组、模型白名单 |
| 3 | Key 管理：管理端代创建、明文交付、单 Key 停用 |
| 4 | 请求治理：用户与账号并发、RPM 限流 |
| 5 | 额度：按人每日 Token 额度，四类 token 同等计权 |
| 6 | 用量：按人 / Key / 模型 / 时间查询 |
| 7 | 停用：用户级停用与 Key 级停用 |
| 8 | 编程 Agent 支持：工具调用经原生聊天透传路径 |

### 3.2 不包含范围

| # | 非目标 | 说明 |
| --- | --- | --- |
| 1 | 研发人员登录平台 | 仅用 Key 调用；用户记录作为归属与统计容器 |
| 2 | Key 自动到期 | 收回依赖停用 |
| 3 | Key 自动轮换 | 首版手工交付 |
| 4 | 上下文的网关层限制 | 交由上游模型拦截 |
| 5 | 按周 / 月额度 | 首版只做每日 |
| 6 | 精确计费 | 额度是防滥用配额，不追求与上游账单一致 |
| 7 | 模型服务的部署与运维 | 属模块二 |
| 8 | GPU 与基础设施管理 | 属模块三 |
| 9 | 监控、告警与审计 | 属模块四 |
| 10 | 多租户与对外开放 | 仅服务本团队内部 |

## 4. 核心原则

- **数据不出内网。** 模型推理与业务数据均在内网完成，这是自建的根本理由，任何设计不得破坏它。
- **凭证不落明文于日志。** 验证与运行输出不得包含 API key、token、密码或完整敏感环境变量。
- **能力结论须有证据。** 区分"源码依据"、"配置后可用"、"待验证"三档；不以 README 或目录名推断能力。
- **配额定位为防滥用，而非精确计费。** 允许在并发在途请求下小幅超出，不将其视为缺陷。
- **优先复用脚手架，改造控制在必要范围。** 新增开发集中在管理端代发 Key 与额度计量口径两处。

## 5. 方案概述

### 5.1 候选方案

- **方案 A：以 Sub2API 为脚手架。** 复用其多用户、分组授权、上游账号、Key 管理、并发控制与用量统计，新增管理端代发 Key，改造额度计量为 Token。
- **方案 B：以 New API 或 LiteLLM 为脚手架。** 前两者的最小改造清单已在调研中比较。
- **方案 C：自研。** 完全自建网关与业务管理。

### 5.2 当前选择

- 选择方案：**方案 A（Sub2API）**。
- 选择理由：调研确认其现成能力可覆盖首版主要环节，新增开发量最小；两套配额体系中的 `user_platform_quotas` 在结构上已可承载"每人每日 Token 额度"，管理员接口已存在。
- 参考：[源码核对](../../temp/research/sub2api-source-review.md)、[候选比较](../../temp/research/source-review.md)。

详细模块、接口、数据流与技术决策记录在 `design.md` 中。

## 6. 风险与限制

| 风险或限制 | 影响 | 应对方式 | 状态 |
| --- | --- | --- | --- |
| vLLM 上 `reasoning_content` 与 `tool_calls` 是否同现未知 | 若同现，客户端多轮工具调用可能报 400，Agent 场景失效 | 层级 2 运行时验证；必要时在 vLLM 侧不产出思考内容 | open |
| Sub2API 不解析 DeepSeek 缓存字段 | 缓存命中计入 `input_tokens`，额度读数高于上游账单口径 | 确认可接受即不改；若需对齐则补映射 | open |
| 额度检查与用量累加不同步（TOCTOU） | 并发在途请求可小幅超出额度 | 明确其为配额而非计费，验收标准不按精确值设定 | open |
| 上游若不返回 usage，额度静默失效 | 额度对任何人不生效 | 透传路径已强制 `include_usage`；运行时验证上游配合程度 | open |
| 管理端无代发 Key 能力，需新开发 | 首版关键路径上的新增开发 | 底层服务已接收 userID，改造范围可控 | open |
| 列表接口返回完整明文 Key | 明文暴露面大于预期 | 设计阶段决定是否在响应层截断 | open |
| 依赖 vLLM 部署先行 | 模块一无法独立验证 | 与模块二对齐部署要求清单；模块三尽早启动 | open |
| 技术栈尚未最终确认 | 无法形成稳定的模块设计 | 本 Spec 限定在模块一范围内 | open |

## 7. 待确认问题

- **思考模式的开闭策略**：是否需要 vLLM 侧默认关闭思考模式，或将"不产出思考内容"写入部署要求。
- **额度计量改造的范围**：累加点与判断点已定位，具体改造量取决于字段类型与入口集中度，待 `design.md` 确认。
- **`platform` 字段映射方案**：借用一个白名单内的平台 key，其长期可维护性待评估。
- **`*_usd` 字段的页面呈现**：字段名仍为 `*_usd`，界面如何显示为 Token 待定。
- **列表接口明文暴露的取舍**：是否截断。
- **源码纳入仓库方案**：固定版本、代码位置、许可证保留与后续同步方式。
- **验证执行方式**：层级 2 由谁执行（当前仅授权层级 1）。
